AGENT HARNESS DESIGN // 项目自述

Office Agent：让 LLM 编辑真实 Word / Excel 文档，
但从不相信它自己说"改好了"

一个跑在 Mac 上的自然语言文档编辑 agent。核心不是"LLM 调工具"，而是它下面那套 闭环控制系统：每一步编辑都要经过 Word/Excel 本体真实渲染出的截图、 交给一个完全独立、无状态的视觉验证器裁决，执行者永远不能给自己的作业打分； 失败会被归一化成"签名"，同一类失败会触发换策略乃至问用户，而不是无限重试。

PROBLEM // 问题

为什么不能只靠 Prompt

"让 LLM 调 python-docx / openpyxl 工具，相信它自己汇报'已成功编辑'"——对真实办公文档来说是不安全的。 这套 harness 要正面解决的是 5 类具体、可复现的工程风险，而不是抽象的"agent 可靠性"口号。

自证偏差

执行者的自我汇报不可信。"我成功把字体改了"是模型自己的叙述，不是文档真的长什么样的证据——需要一个只看像素、不看执行过程的独立裁判。

签名碰撞

错误文本每次都不一样。不同单元格、不同缺失的词——朴素的字符串匹配永远发现不了"这是同一类错",重试逻辑会在一个坏思路上无限循环。

决策失效

用户的显式决定必须真正生效。如果"中止/跳过"的执行依赖模型在下一轮正确读懂并服从一个 tool_result，那这个决定随时可能被模型忽略或曲解。

静默丢数据

openpyxl 的 writer 会静默丢弃它不认识的 OOXML 部件。一次普通的保存就可能不可逆地丢失图表、透视表、批注——除非有东西主动去检查。

自动化悬挂

macOS 自动化真实 Office App 极易"隐形挂起"。权限弹窗、覆盖确认框、甚至连"检查目录能不能读"这种系统调用本身都会挂起而不是抛异常——普通的异常处理模型根本观察不到。

  • harness 核心 —— 驱动 plan → execute → render → verify → escalate 这一整个循环；拥有全部控制流状态（计划状态、每步预算、abort 标志、"哪些文档还有未验证的改动"），唯一有权判定一步"完成"的地方。
  • 工具层 —— 把 pydantic 模型直接变成 Anthropic tool schema，用统一的 {success, error, error_type} 信封包裹每个 handler，成功的 mutating 调用自动打快照；选择器解析对"结构性错误"和"内容没匹配到"给出不同的契约（抛异常 vs 返回空列表）。
  • 文档适配层 —— 纯 @staticmethod，对已经打开的 worksheet/Document 做原地修改，返回 JSON-safe 的 affected 清单；这里是唯一懂 OOXML/openpyxl 对象模型细节（字体、边框 XML、图表 Reference range、run 拼接）的地方。
  • 渲染 + 视觉验证闭环 —— 用零弹窗 AppleScript 把真实文档导出 PDF，栅格化成 PNG，把改动前后的像素做 diff（且永远只对着"上一次通过验证的基线"diff，绝不是"上一次任意一次渲染"），把改动区域裁给独立验证器。
  • 会话隔离与安全边界 —— 把目标文件复制进 App 自己的沙盒容器（这样渲染永远不会触发权限弹窗），所有写回磁盘的操作都要过两道独立的同意闸门（覆盖闸门 + Excel 保真度闸门），并实现基于全量字节快照的 undo/redo。
  • LLM 客户端 / 终端 UI / 离线测试 —— 对 Anthropic SDK 的一层薄封装（指向 MiniMax-M3 的 Anthropic 兼容端点），Rich + questionary 的终端 UX，以及一个和真实客户端调用签名完全一致的 FakeLLM，让整条控制流可以在零网络依赖下被确定性地测试。

ANTI BRUTE-FORCE // 反暴力升级梯

同一类失败，两次就必须换打法

agent/budget.py 把任何自由文本的工具报错或验证失败，先归一化成 6 类粗粒度签名之一 （no_match / out_of_range / invalid_args / verify_text / verify_style / verify_layout + other）， 再决定要不要升级。工具报错和视觉验证失败共用同一套签名空间和同一个 StepBudget。

关键代码：一次失败到底走哪条分支

agent/budget.py:99-118
def record_failure(self, step_index: int, signature: str) -> Action:
    budget = self.step(step_index)
    budget.attempts += 1
    budget.signatures.append(signature)

    if budget.attempts >= self.limits.max_attempts_per_step:
        return Action.ASK_USER
    if budget.strategy_switched and signature == budget.switched_signature:
        # 这一类失败已经切换过策略、还是同样失败——
        # 换一个全新签名会拿到自己独立的一轮升级梯，而不会继承这次的升级状态
        return Action.ASK_USER
    recent = budget.signatures[-self.limits.same_error_strategy_switch:]
    if len(recent) == self.limits.same_error_strategy_switch and len(set(recent)) == 1:
        budget.strategy_switched = True
        budget.switched_signature = signature
        return Action.SWITCH_STRATEGY
为什么这样设计：不同单元格地址、不同缺失的词——自由文本错误每次都不一样，精确字符串匹配永远发现不了"这是同一类错"。归一化成签名之后，"同一类失败连续出现"才第一次变成一个可以被代码判断的条件。
KEY MECHANISMS // 关键机制

9 个真正"耐问"的设计细节

每张卡片：机制 → 代码 → 为什么存在 → 面试里怎么讲这一点。

1 · 独立无状态视觉验证器，失败即拒绝通过

agent/verifier.py:1-6, 104-141

verify_edit() 是一次独立的一次性 LLM 调用，只拿到步骤意图 + 操作摘要 + 改动前后的图片——从不看执行者的对话历史或它自称的"成功"。tool_choice 被强制指向 report_verification；连续两次解析不出裁决结构，直接返回 passed=False, severity=blocking，而不是默认放行。

如果验证器读到执行者的自夸叙述，判断会被那段叙述"锚定"而倾向盖章通过。失败关闭（fail-closed）意味着一次 LLM API 抖动永远不可能被误判成"验证通过"——它只会多花一轮升级梯。
面试话术真正的 actor / critic 分离：改文档的模型永远不给自己判卷，而判卷的模型一旦坏了，默认结果是"重做"，不是"放行"。

2 · Baseline 棘轮：diff 永远对着"上次验证通过"的状态

agent/loop.py:583-633 · render/renderer.py:24-28

Renderer 维护两个指针：previous（每次渲染都覆盖）和 baseline（只在 verify_edit 返回通过后，由 agent loop 显式推进）。_verify_doc 永远对 baseline 做 diff，不是对 previous。

如果 diff 基准是 previous，模型可以在标记 done 前先调一次无意义的 render_preview，让下一次真正的验证 diff 出来的差异被"稀释"到接近于零——一次真实的回归可以藏在一次"无变化"的预览背后。基线锚定把这条路堵死。
面试话术正确性的参照系是一个只会前进的棘轮，不是一个随便移动的指针——和 git bisect 的 good/bad 边界是同一个思路。

3 · 用户的决定，用代码强制生效，而不是"告诉模型"

agent/loop.py:481-531

当升级到 ASK_USER，harness 直接弹出固定的多选题（换个方式再试 / 跳过 / 中止），然后解析用户的回答文本，直接修改 session 状态——abort_requested=True、plan.set_status(...,'blocked')、或 step_budget.refresh_ladder()——而不是把结果当成一条 tool_result 期待模型自己去理解和服从。每步最多问 2 次，超了自动中止。

模型读到"用户说跳过，请照办"仍然只是一条建议，它下一轮完全可能忽略或误读。把效果直接写死在 Python 里，才能保证用户的选择无论模型接下来做什么都真正生效。
面试话术回答"你怎么保证 agent 真的服从用户的干预"这个问题的标准答案：决策效果通过直接改变会话状态来强制执行，不是寄希望于模型正确读懂一条工具结果。

4 · tool_use / tool_result 配对，在中止和内部崩溃下都不能破

agent/loop.py:160-221

一旦 abort_requested 置位，同一批里剩下的每个 tool_use 仍然会拿到一个合成的错误 tool_result（"排队中的调用未执行"），而不是被直接丢弃；_handle_tool 又用一层 except Exception 把任何内部 bug 转成同样形状的错误信封。

Anthropic Messages API 要求下一轮 user 消息里，每个 tool_use 必须严格对应一个 tool_result——少一个就是格式错误的请求，整个会话上下文作废。这个不变式针对"用户中止"和"内部代码 bug"两种触发源，被独立地各加固了一次。
面试话术同一个 API 不变式被两条完全不同的失败路径分别兜住——说明这两类失败是被分开推演过的，不是"加一个 try/except 糊住所有情况"。

5 · 两道相互独立的保存同意闸门，复用同一条异常通路

core/session.py:35-40, 261-287

save_to() 对"覆盖原文件 / 覆盖任何已存在的其他文件"和"静默丢失 Excel 保真度"分别抛出两种不同的异常：普通 PermissionError 与 FidelityLossError。后者刻意继承 PermissionError，这样它能不做任何改动就流经 ToolRegistry.dispatch 已有的捕获元组。

"覆盖文件"和"静默丢内容"是两种性质不同的风险，理应各自可审计、各自需要单独同意，而不是合并成一个笼统的 force 开关。新增的安全闸门通过挑选一个恰当的基类，零改动地接入了已有的错误处理管线。
面试话术回答"怎么在不扩大公共代码爆炸半径的前提下加一道新的安全闸门"——答案是让新异常的基类恰好命中现有的 catch 元组，而不是去改调度器。

6 · 零弹窗 macOS Office 自动化：双层超时 + 错误分类器 + 全局锁

render/applescript.py:16-18, 37-75, 85-136

每次导出都跑在 AppleScript 自身的 timeout 块和外层 subprocess timeout（多 5 秒）双重保护下；stderr 被模式匹配进一个类型化异常体系（AutomationDenied / RenderTimeout / DocumentCorrupted）；一把进程级全局锁串行化所有 Word/Excel 脚本调用（因为 active document 这类引用在并发脚本间是有歧义的）；App 永远不会被 activate；导出前先删掉可能存在的旧 PDF 以绕开覆盖确认框。

无人值守的文档自动化极易"隐形挂起"（权限弹窗、覆盖确认），这是普通 Python 异常模型完全观察不到的失败类别。模块自己的 docstring 就是这份设计规格，每条不变式都能对应到文件里的一行具体代码。
面试话术整个项目里"系统工程而不只是 prompt 工程"证据最硬的一块——能准确说出 -1712 / -1743 这些 AppleScript 错误码分别代表什么、为什么修复方式不是简单 try/except。

7 · Excel 保真度守卫：用"部件清单 diff"取代被证伪的启发式

core/session.py:43-89, 165-185, 279-287

_zip_inventory() 只读 zip 的中央目录（不解压），对比原文件和试序列化后的工作副本，任何在基线里出现、保存时却消失的成员都会被按 OOXML 部件家族分类并拦下保存，除非显式传入 accept_fidelity_loss=True。这替换了此项目早期"按子串/图表名匹配"的启发式——那个启发式被自己的测试证明会在自己生成的图表上误报。

openpyxl 对它对象模型不认识的任何部件都会静默丢弃；一个基于"部件名字是否还在"的结构性 diff 能通用地抓住这一类问题，不需要针对每种新特性写解析逻辑，也天然避开了"按大小 diff 一定会全量误报"的陷阱（哪怕无损往返，字节大小也会变）。
面试话术一个完整的自我纠错故事：上线一个启发式 → 被自己的测试证明在一个具体场景下是错的 → 换成一个经过假阳性和真阳性双重测试验证的机械不变量。

8 · TCC 沙盒容器：把工作副本放进 App 自己的容器里

core/session.py:91-129

work_root_for() 默认把会话工作目录放进 ~/Library/Containers/com.microsoft.{Word,Excel}/...；而检查这个容器能不能访问这件事本身，在没有 TCC 授权的情况下会直接挂起而不是抛异常——所以探测代码把它包进一个带 3 秒硬超时的子进程（/bin/ls），而不是直接在主进程里做文件系统调用。

App 对自己的容器本来就有权限，把工作副本放进去就永远不会触发权限弹窗；用可被杀死的子进程去做探测，能在探测本身就可能挂起的情况下优雅降级到备用目录，而不是冻结整个会话。
面试话术"挂起"和"异常"是两种完全不同的失败模式——异常能 catch，挂起只能用超时从外部拦腰斩断,这是很多人不会主动想到的一层。

9 · FakeLLM：签名对齐到位、失败就大声报错的离线测试替身

tests/fake_llm.py:34-57

FakeLLM.create 的参数签名（system, messages, tools, tool_choice, max_tokens）和真实客户端完全一致，AgentSession 和独立验证器都无法分辨；被强制 tool_choice 指向 report_verification 的调用会被路由进单独的 verify_script 队列；脚本耗尽或出现没预期到的调用，直接 AssertionError，绝不返回一个"看起来还算合理"的默认值。

让整条控制流——计划、工具执行、升级梯、预算耗尽、保存闸门、验证→修复——可以在零网络依赖下被确定性地跑一遍;而"大声失败"意味着测试脚本和真实 harness 行为一旦不匹配,会在当场就暴露,而不是在后面几步之后变成一个难以定位的诡异失败。
面试话术直接回答"你怎么在没有真实 LLM 的情况下测试一个 agent"——让替身精确匹配调用签名，让它坏得响亮而不是坏得含糊。
TRADEOFFS // 设计决策与权衡

每个决定，都对应一个被放弃的替代方案

按 情境 → 决定 → 权衡 → 结果 的结构整理，方便被追问"为什么不这样做"时直接引用。

情境
工具报错、和"调用成功但视觉上错了"，是两种性质不同的失败。
决定
让它们共用同一套签名归一化 + 升级梯，同一个 StepBudget、同一个签名空间。
权衡
一个 verify_style 失败理论上可能和同一步里一个不相关的 invalid_args 报错共用同一个尝试次数上限。
结果
用一套机制同时覆盖"工具级"和"视觉验证级"两类无效循环，而不是维护两套反暴力逻辑。
情境
每次视觉验证都要付出一次真实渲染 + 一次额外 LLM 调用的代价。
决定
对 NON_VISUAL_TOOLS = {excel_write_cells, excel_edit_formula} 整体跳过视觉验证。
权衡
正确性依赖这份白名单保持准确——未来一个"看似非视觉"却实际影响排版的工具，会悄悄绕过验证，除非有人记得同步这份清单。
结果
纯数据编辑省下真实、可观的成本和延迟。
情境
ask_user 升级后，决定必须真正生效，不能只是"模型看得到"。
决定
对用户选择的答案文本做硬编码前缀解析，直接改 abort_requested / plan 状态 / 预算，而不是让模型自己解读。
权衡
控制流耦合到 UI 选项文案的具体前缀——如果未来改了选项措辞却没同步这里的解析，强制生效会静默失效。
结果
用户的中止/跳过决定，无论模型接下来做什么，都能确定性生效；每步最多问 2 次自动中止。
情境
上线的 Excel 数据丢失启发式（子串/图表名匹配）被自己的测试证明会假阳性——在自己生成的图表上误报。
决定
换成加载 → 试序列化 → zip 部件清单 diff，只按"部件名字是否还在"判断，绝不按大小判断，一次性算好，保存时拦截。
权衡
每次打开文档多付出一次整表试序列化的开销，在 2 万行规模下的延迟在上线时被明确标注为"尚未做过基准测试"。
结果
已上线（commit 9f7a5b5），假阳性回归测试和真阳性阻断测试同时通过。
情境
在目标 App 自己的沙盒容器之外自动化渲染文档，会触发 macOS TCC 权限弹窗；连"检查容器能不能读"本身都可能挂起而不是报错。
决定
默认把工作副本放进目标 App 自己的容器，并用带 3 秒硬超时的子进程去探测可访问性，而不是直接在主进程里做文件系统检查。
权衡
渲染子系统被绑死在一条 macOS 专属、按 App 区分的沙盒路径上，而不是一个可移植的通用临时目录；每个会话多一次整文件拷贝。
结果
零弹窗自动化不变式，被 office-agent doctor 里一次真实的端到端渲染冒烟测试持续验证。

四个"具体到能讲成故事"的坑

结构性腐化

Word "链接到上一节" 的页眉/页脚共享同一段 XML。直接编辑会静默改写更早页面的内容。选择器解析器检测 is_linked_to_previous，往前回溯找到真正拥有这段定义的 section，抛出命名了正确 owner 的 SelectorError，而不是悄悄返回共享的段落。selector_parser.py:112-133

Flaky 插入

TEST DISCIPLINE // 测试与验证纪律

怎么测试一个没有真实 LLM 的 agent

  • FakeLLM 精确对齐调用签名。让 AgentSession 和独立验证器都分辨不出这是不是真实客户端，从而能把计划、执行、升级梯、预算耗尽、保存闸门、验证→修复整条控制流在零网络依赖下跑一遍。
  • 验证器专用的独立脚本队列，耗尽即报错。主循环脚本不需要预测验证调用具体在哪一步插入；一旦队列耗尽或来了没预期到的调用，直接 AssertionError，不会悄悄返回一个"看起来还行"的默认值。
  • 精确计数断言，不是"真值/存在性"断言。比如 after.count('_SUFFIX') == 1、len(session.doc[sheet]._charts) == 1——一个 truthy 检查即使某次编辑被误执行了两遍照样能通过，只有精确相等才能抓住"预览/应用被执行了两次"这类回归。
  • 覆盖闸门测试直接断言原文件的字节没被动过。而不是只检查函数返回值，验证的是"拒绝覆盖"这个安全边界的真实作用范围。
  • Excel 保真度守卫同时有假阳性回归测试和真阳性阻断测试。前者覆盖 openpyxl 原生特性（图表、条件格式、表格、合并单元格）确认能无损往返，后者覆盖真正会被 openpyxl 丢弃的部件（线程批注、切片器缓存、自定义 XML）确认会被正确拦截。
  • doctor 自检跑的是真实端到端渲染路径,不是静态检查。它要守护的具体失败模式——无人值守渲染时冒出权限弹窗——只有真的走一遍真实路径才能证明不存在;而且只会退出它自己为了自检而启动的 App 实例,绝不影响用户本来就开着的文档。
EXTENSIBILITY // 面向未来的设计

三份"先探针、再设计"的扩展提案

这些还没有实现，但同样值得在面试里讲——它们展示的是系统设计判断力：怎么在 python-docx / openpyxl 的天花板之上继续扩展，而不破坏已有的安全模型和 render+verify 闭环。三份文档都遵循同一条纪律： 每个不明显的结论都要有一次真实探针（osascript 干跑、zip 手术、读已安装库源码）支撑，失败和成功一样被诚实记录。

DOCS/EDIT-LAYER-DESIGNS/ROUTER-NATIVE-OPS.MD

Native-Ops Router —— 用一个封闭、手工验证过的 AppleScript 模板库，覆盖"整份文档级"操作

比如接受/拒绝全部修订、更新全部域、重新计算工作簿——这些在 python-docx/openpyxl 里根本没有对应模型。执行序列固定为 flush → 快照 → 跑模板 → 失败回滚 / 成功后 reload。设计里把候选能力分成两档：Tier-1 能安全 reload 回内存对象， Tier-2（透视表刷新、工作表保护）被设计成"只在最终落盘时跑一次的收尾工序，绝不 reload 回活跃会话"——因为下一次 openpyxl 保存会静默把它刚修好的东西又冲掉。

明确拒绝的替代方案——自由生成 AppleScript 脚本，或一个"受限 DSL"折中方案：AppleScript 的 tell application 能指向任意已安装的可脚本化应用，do shell script 能跑任意命令——这是一个跨应用、等同于 RCE 的攻击面，而不只是 docx 损坏风险,也会让失败签名归一化机制彻底失效（失败方式不可枚举）。
DOCS/EDIT-LAYER-DESIGNS/EXCEL-FIDELITY-GUARD.MD

已实现部分背后的完整推理：为什么按"部件名字"而不是"字节大小"判断丢失

探针证明哪怕一次完全无损的往返，字节大小也几乎必然变化（空白、属性顺序）；按大小触发会在几乎每一次保存上都假阳性， 训练用户和 agent 一起学会无视这条警告——这正是旧启发式已经证明过的失败模式。FidelityLossError 继承 PermissionError，零改动接入已有的调度器捕获元组。

被否决的兜底方案——发现丢失后自动切到原始 XML 解包/编辑/重打包管线：这条路只能解决"简单一半"的问题（单元格值、样式）， 永远救不回图表/透视表/切片器这些真正重要的部分，还会引入第二条更难验证的写入路径,与"信任文件结构、靠真实渲染验证"的核心思路相悖。
DOCS/EDIT-LAYER-DESIGNS/XML-PATCH-WORD.MD

xml_query / xml_patch —— 直接在活的 python-docx lxml 树上做 XPath 级操作

用来够到脚注、尾注、域、修订接受/拒绝这些结构化工具完全碰不到的内容。三层校验：片段是否 well-formed → 落盘后独立重新打开做探测性读取（任何异常整体回滚） → 已有的真实渲染 + 独立多模态验证。刻意不建一个完整的 XSD 模式校验层——探针已经证实 lxml 和 python-docx 的 OPC 层完全不做模式校验， 而 Word 本身对至少一些模式非法的嵌套（比如 <w:tbl> 嵌在 <w:r> 里）也能零弹窗导出——"模式干净"不足以保证正确， "模式脏"也不一定真的有害，render+verify 闭环才是真正的事实来源。

被否决的设计——先解包 zip、编辑文件、再打包回去的独立流水线（类似某些 Anthropic skill / PPTArena 的模式）： doc.part.package 已经给了完整的内存级访问，第二条流水线只会需要和活的内存对象保持同步，却拿不到相应的好处。
Q&A REHEARSAL // 面试问答预案

压轴：追问清单

Q1你怎么防止 agent 自己给自己的作业打满分？
独立、无状态的验证器只看步骤意图 + 渲染出的前后图片,完全看不到执行者的对话历史或它自称的"成功"——actor 和 critic 被物理分离。而且验证器解析失败时默认是 passed=False,不是默认放行。
Q2报错信息每次都长得不一样,你怎么判断"这是同一类失败"?
先把自由文本归一化成 6 类粗粒度签名(no_match / out_of_range / invalid_args / verify_text / verify_style / verify_layout),再判断同一个签名是不是连续出现——这样不同单元格地址、不同缺失的词都能被识别成"同一类问题"。
Q3用户说"中止",你怎么保证 agent 真的停下来,而不是模型下一轮又继续?
升级到 ASK_USER 之后,用户的答案不是作为一条 tool_result 交给模型自己解读,而是直接被 harness 解析并写进会话状态(abort_requested / plan 状态 / 预算),用代码强制生效。
Q4为什么不能直接拿"上一次渲染"做 diff 基准?
因为模型可以在标记 done 之前先调一次无意义的预览渲染,让"新渲染 vs 刚预览的渲染"没有差异,从而让一次真实的回归看起来像"什么都没变"。所以 diff 基准是上一次验证通过的渲染(baseline),只在验证通过后才前移,预览渲染永远不会移动它。
Q5用 AppleScript 自动化真实 Office App,最坑的地方是什么?
不是报错,是"隐形挂起"——权限弹窗、覆盖确认框,甚至连"检查一个目录能不能读"这个系统调用本身,在没有 TCC 授权时都会直接挂起而不是抛异常。应对方式是双层超时(AppleScript 自身 timeout + 更长的外层 subprocess timeout)、把探测本身也包进带硬超时的子进程、以及把工作副本放进 App 自己的沙盒容器来从源头避免弹窗。
Q6Excel 数据丢失这个坑,是怎么被发现、又是怎么解决的?
最早上线的是一个按子串/图表名匹配的启发式,后来被项目自己的测试证明会在自己生成的图表上误报——一个已知为错的检测方式。换成了"加载→试序列化→按 zip 部件名字 diff"的机械检查,明确只按"部件是否还在"判断、不按字节大小判断(因为哪怕无损往返大小也会变),保存前默认拦截,需要显式同意才能继续。
Q7没有真实 LLM,你怎么测试整条 agent 控制流?
写一个 FakeLLM,参数签名和真实客户端完全一致,agent loop 和验证器都分辨不出区别;验证调用被单独路由到一个 verify_script 队列;一旦脚本耗尽或来了没预期到的调用,直接 AssertionError——失败要失败得响亮,不能悄悄返回一个看起来合理的默认值。
Q8如果要扩展到修订记录、脚注这些 python-docx 完全碰不到的内容,你会怎么设计?
加两个新工具 xml_query / xml_patch,直接在活的 lxml 树上做 XPath 级操作,三层校验(片段合法性 → 落盘后独立重新打开探测 → 已有的真实渲染+验证闭环),刻意不建完整的 XSD 校验层——因为已经用真实探针证实了"模式干净"不等于正确、"模式脏"也不一定有害,render+verify 才是唯一的事实来源。
Q9为什么不干脆做一个能跑任意 AppleScript 的通用工具,岂不是更灵活?
因为 AppleScript 的 tell application 能指向任何已安装的可脚本化应用,do shell script 能跑任意命令——那是一个跨应用、等同于任意代码执行的攻击面,而不只是文档损坏的风险,而且会让失败签名归一化彻底失效,因为失败方式变得不可枚举。所以选择的是一个封闭、每条都手工验证过的模板库,新能力要先有真实 osascript 干跑记录才能合入。
